# Design

## Context

프로젝트는 비어 있다(`openspec/`만 존재). Node 24, npm, git은 설치돼 있다. 동기와 범위는 proposal.md를 따른다.

제약:
- 개발자는 입문자다. 설정 단계와 새 개념의 수를 최소화한다.
- 카카오 로컬 REST API는 `Authorization: KakaoAK {REST_API_KEY}` 헤더가 필요해서 브라우저 직접 호출은 불가한 것으로 문서 요약에 나왔다(미검증 추정 포함). 반면 카카오맵 JS SDK의 `services` 라이브러리는 브라우저에서 JavaScript 키 + 도메인 등록으로 장소 검색을 제공하는 것으로 알고 있다(구현 첫 단계에서 검증).
- 나중에 앱인토스 WebView에 올릴 가능성이 있다. 앱인토스는 허용 도메인이 `<appName>.apps.tossmini.com` 형태이고, 같은 환경에서 카카오맵 SDK 로드가 실패했다는 보고가 있어 확정되지 않았다.

## Goals / Non-Goals

**Goals:**
- 서버 없이 동작하는 정적 웹앱으로 MVP(주변 목록, 지도, 검색, 상세)를 완성한다.
- 위치 조회와 장소 검색과 지도 렌더링을 인터페이스 뒤로 분리해, 앱인토스 이식 시 구현만 교체할 수 있게 한다.

**Non-Goals:**
- 로그인, 즐겨찾기, 리뷰, DB, 해외 지역.
- 앱인토스 출시 자체와 SDK 연동 구현(별도 후속 작업).
- 카카오 데이터를 자체 저장소에 보관하거나 캐싱하는 것.

## Decisions

**1. 프런트엔드: Vite + React + TypeScript (SPA)**
앱인토스 WebView가 Vite+React+TS를 공식 지원하므로 이식 비용이 낮다. 대안인 Next.js는 서버 렌더링 이점이 이 앱에 없고 학습 부담만 늘린다. 순수 JS는 가능하지만 외부 API 응답 타입을 다루는 연습과 이식 시 안전성 면에서 TS가 낫다.

**2. 장소 검색: 카카오맵 JS SDK `services.Places`를 브라우저에서 직접 사용 (기본안)**
서버와 비밀키 관리가 필요 없어 입문자에게 가장 단순하다. 위치 + 반경 + 거리순 + 음식점 카테고리(FD6) 필터와 페이지 이동을 지원하는 것으로 알고 있다. 키는 도메인 등록으로 보호한다.
- 대안: 서버리스 함수로 REST API를 중계(Vercel/Cloudflare). 비밀키를 숨기고 자유도가 높지만 배포 구성이 늘어난다.
- 결정 방식: 첫 작업에서 `services.Places`로 실제 요청이 되는지 검증한다. 검증이 실패하면 중계 서버안으로 전환하고, 이 경우 검색 어댑터(결정 3)의 구현만 바꾼다.

**3. 경계 분리: 세 개의 어댑터 인터페이스**
UI는 구체 SDK를 모르고 아래 인터페이스만 사용한다.
```
 +------------------+     +---------------------+     +------------------+
 | LocationProvider | --> | PlaceSearchService  | --> |  MapView         |
 | getCurrentPos()  |     | searchNearby()      |     |  renderMarkers() |
 | (브라우저 GPS)    |     | searchByKeyword()   |     |  (카카오맵)       |
 +------------------+     +---------------------+     +------------------+
   앱인토스: SDK 위치 API     중계 서버로 교체 가능       다른 지도로 교체 가능
```
도메인 모델은 SDK 타입과 분리된 자체 `Restaurant`(id, name, category, address, phone, lat, lng, distance, placeUrl)로 두고, 어댑터가 카카오 응답을 이 모델로 변환한다. 이 변환 함수는 순수 함수라 단위 테스트하기 쉽다.

**4. 상태 관리: React 내장 상태(useState/useReducer)**
화면 상태(위치, 목록, 선택, 검색어, 로딩/오류)가 한 화면 안에 있어 외부 상태 라이브러리가 필요 없다. 대안인 Zustand/Redux는 이 규모에서 과하다.

**5. 화면 구성: 한 화면 + 상세 패널**
모바일 우선. 위쪽 지도, 아래쪽 검색창과 목록, 선택 시 상세 패널(하단 시트)이 열린다. 데스크톱에서는 좌측 목록, 우측 지도. 라우터 없이 선택 상태만으로 처리한다.

**6. 키와 설정: 환경 변수**
`VITE_KAKAO_JS_KEY`를 `.env.local`에 두고 저장소에는 `.env.example`만 커밋한다. JS 키는 브라우저에 노출되는 값이므로 보안은 카카오 앱 설정의 도메인 등록에 의존한다. REST 키가 필요해지면(중계안) 서버 쪽 환경 변수로만 둔다.

**7. 배포: 정적 호스팅(Vercel 또는 Netlify 무료 플랜)**
배포 후 도메인을 카카오 앱 설정에 추가해야 지도와 검색이 동작한다.

**8. 테스트: Vitest**
변환 함수, 거리 포맷, 상태 전환 같은 순수 로직은 단위 테스트한다. 지도와 외부 호출은 어댑터를 가짜로 바꿔 UI 동작을 확인한다. 실제 지도 렌더링은 수동 확인으로 둔다.

## Risks / Trade-offs

- [JS SDK `services`가 기대한 옵션(반경, 거리순, 카테고리)을 지원하지 않을 수 있음] → 첫 작업에서 검증하고, 실패 시 서버리스 중계로 전환(어댑터만 교체).
- [지도와 검색이 같은 카카오 SDK에 의존하므로, SDK 로드 실패 시 지도와 목록이 함께 실패함] → 지도 초기화 실패만 격리해 목록을 유지하고, SDK 로드 실패는 일반 검색 오류(다시 시도 가능)로 처리. 이 결합을 없애려면 REST + 중계 서버가 필요하나 이 앱의 규모에 비해 과해 채택하지 않음.
- [JS 키가 노출됨] → 도메인 등록 제한, 비밀이 아닌 키임을 문서화, REST 키는 절대 프런트에 넣지 않음.
- [카카오 무료 할당량 초과] → 개인 학습 규모에서는 낮은 위험. 검색 입력에 디바운스/제출 방식을 써서 불필요한 호출을 줄임.
- [브라우저 GPS가 데스크톱에서 부정확하거나 HTTP 환경에서 막힘] → 배포는 HTTPS, 개발은 `localhost`(보안 컨텍스트로 취급됨). 실패 시 스펙대로 안내와 키워드 검색으로 대체.
- [앱인토스 WebView에서 카카오맵이 로드되지 않을 수 있음] → MVP 범위 밖. 지도와 위치를 어댑터로 분리해 두고, 이식 단계에서 먼저 빈 앱으로 로드 테스트 후 네이버 지도 등으로 교체 가능성을 검토.
- [카카오 데이터 약관] → 상세 화면에서 카카오맵 링크로 출처를 보여주고, 데이터를 저장하거나 재배포하지 않음.

## Open Questions

- 기본 반경 1km가 적절한지(도심과 외곽에서 결과 수가 크게 다를 수 있음). 구현 후 실사용으로 조정해도 스펙의 "기본 반경" 외에 영향이 없다.
